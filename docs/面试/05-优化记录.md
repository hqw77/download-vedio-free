## 1. AI 流改成真异步（P0-2）

### 问题

`api_summarize.py` 的 SSE 生成器里：

```python
for token in summarizer.summarize_stream(...):
    yield ...
```

`summarize_stream` 内部是同步 `OpenAI` 客户端。每取一个 token 都阻塞在网络读上，**整个事件循环被占住**：其他请求、`/api/health`、并发 SSE 全部排队。

### 改动

- `summarizer.py`：`OpenAI` → `AsyncOpenAI`；`summarize_stream`、`generate_mindmap`、`chat_stream` 改成 `async`。
- 流式调用改为 `await client.chat.completions.create(..., stream=True)` + `async for chunk in response`。
- `api_summarize.py`：`for token` → `async for token`；思维导图从 `run_in_executor` 改为 `await summarizer.generate_mindmap(...)`。

### 验证

本地 B 站视频（`BV1mAAmzqEfP`）总结，同时每 300ms 请求一次 `/api/health`：

| 指标 | 结果 |
|---|---|
| 总结耗时 | 12.1s |
| `summary` 事件 | 1142 个 |
| 思维导图 | 1033 字 |
| health 采样 | 39 次 |
| health 平均延迟 | 3ms |
| health 最大延迟 | 92ms |

总结进行中，健康检查仍然毫秒级返回，说明事件循环没有再被阻塞。

### 面试话术

> “我发现 SSE 生成器里在同步迭代 OpenAI 流，一个用户总结时整个事件循环被占住。换成 AsyncOpenAI 后，总结期间 39 次 health 采样平均 3ms、最大 92ms，其他请求不再排队。”

## 2. chat 接入登录与配额（P0-1）

### 问题

`/api/chat` 只注入了 `get_optional_user`，但**从未使用 `user`**：未登录也能无限问答。定价页把 AI 问答列为 VIP 能力，代码和产品承诺不一致，也会放大 DeepSeek 成本。

### 改动

- `api_summarize.py` 的 `chat_with_video` 开头调用 `_check_summary_permission(user)`。
- 未登录返回 SSE `error` 事件，`need_login: true`；超限返回 `need_vip: true`。
- 前端 `VideoSummary.vue` 的问答 `error` 回调识别 `need_login` / `need_vip`，弹出登录/升级。

### 验证

不带 token 调 `/api/chat`：

```text
event: error
data: {"message": "请先登录后使用 AI 功能", "need_login": true, "need_vip": false}
```

### 面试话术

> “chat 接口原来把 user 注入了却没用，等于 VIP 功能免费无限用。我把它接入统一的配额检查，未登录直接返回 need_login，前端弹登录框。”

## 3. 配额原子化 + 失败回滚（P1-1 / P1-2）

### 问题

1. `check_and_increment_summary` 是“读 count → 判断 → update”，并发下两个请求都能读到 `count=2` 并同时放行，突破每日 3 次。
2. 配额在字幕提取之前扣；无字幕/解析失败时次数已经扣掉，用户白损失。

### 改动

- `database.py` 改成**单条条件 UPDATE**：
  - 跨天：`CASE WHEN COALESCE(last_summary_date,'') = today THEN count+1 ELSE 1 END`
  - 只有 `last_date <> today OR count < limit` 才更新；
  - 用 `cursor.rowcount` 判断是否成功，再读回 count 算剩余。
- 新增 `refund_summary(user_id)`：失败时退回一次，带 `count > 0` 保护。
- `api_summarize.py` 增加 `_refund_if_needed`：
  - 无字幕 → 退回；
  - 总结/回答还没产出任何 token 就异常 → 退回；
  - 已经产出内容 → 不退回；
  - VIP（`remaining == -1`）不退回。

### 验证

20 个并发调用 `check_and_increment_summary`：

```text
allowed_count 3
results [False, False, ..., True, ..., True, ...]
```

只有 3 次成功。

失败回滚：用一个不存在的视频地址调 `/api/summarize`，报错后再查数据库：

```text
user_id 4 count/date (0, '2026-10-24')
```

配额从 1 退回 0。

### 面试话术

> “原来的配额是读-判断-写，不是原子操作；20 个并发能突破 3 次。我改成条件 UPDATE 看 rowcount，并补了失败退款：无字幕或模型失败时把次数退回，VIP 不退。”

## 1. 自我介绍（两版）

### 1.1 60 秒版

> “我做的项目叫 SaveAny，一个 AI 视频下载与总结工具。用户粘贴视频链接，后端用 yt-dlp 解析 1800+ 平台的可选清晰度并下载；同时提取平台字幕，调用 DeepSeek 做流式总结、思维导图和基于字幕的问答。前端 Vue 3 + Vite + Tailwind，后端 FastAPI + SQLite，认证用 JWT，支付接 Stripe。这个项目主要练三件事：流式 AI 的完整链路、第三方能力的降级设计、从登录配额到支付的商业闭环。我是跟着教程做的，但读源码时发现并验证了几个问题，也做了修复实验。”

### 1.2 两分钟版（推荐）

> “SaveAny 解决的是两个需求：一是把各平台视频下载到本地，二是看长视频前先让 AI 给个摘要和思维导图。
>
> 用户侧很简单：粘贴链接，解析出标题、封面、清晰度和格式，选一个下载；同时右侧自动开始 AI 总结，分四个 Tab：摘要、带时间戳的字幕、可交互的思维导图、以及基于字幕的问答。
>
> 技术上有三条链。第一条是下载：FastAPI 接请求，抖音走专用解析模块，其他平台走 yt-dlp，同步调用丢到线程池；格式会做归一化、去重、排序，最多返回 15 个选项；下载有直链和服务端代理两种模式。
>
> 第二条是 AI：先从 B 站 API 或 yt-dlp 拿字幕，人工字幕优先，其次自动字幕；然后调 DeepSeek 流式生成总结，用 SSE 把 token 推给前端；总结完再生成思维导图 Markdown，前端用 markmap 渲染，并支持导出 4K PNG 和 SVG。SSE 这块前端没有用 EventSource，因为要 POST 和带 Authorization，所以是 fetch + ReadableStream 手写了解析器。
>
> 第三条是账号与钱：bcrypt + JWT 做认证，免费用户每天 3 次总结，VIP 不限；支付用 Stripe Checkout，Webhook 回调里用 pending 状态做幂等，再按 max(now, 到期时间) 叠加会员时长。
>
> 这个项目是教学项目，不是线上高并发系统。但我在读源码时发现并验证了几个真实问题，比如总结流在 async 生成器里同步迭代会阻塞事件循环、chat 接口漏了配额校验、缩略图代理有 SSRF 风险。我做了修复实验，也能说清楚它离生产级还差什么。”

**节奏**：背景 20s → 三条链 80s → 诚实边界 + 亮点 20s。不要一上来报技术栈。

## 4. 五个 STAR 故事（各 90 秒内）

### S1｜SSE 流里的换行把消息拆坏了

- **背景**：流式总结偶发段落丢失、Markdown 错乱。
- **任务**：定位是模型、网络还是协议。
- **行动**：抓 EventStream 原始帧，发现 token 内含 `\n`；SSE 以空行分帧，换行导致一帧被拆成多帧。改为后端对每个 token `json.dumps`，前端 `JSON.parse`，多行 `data:` 用 `\n` 拼接。
- **结果**：格式稳定；形成 `subtitle/summary/mindmap/quota/done/error` 事件契约。
- **反思**：协议边界必须编码，不能假设文本安全；这也是我后来坚持“AI 输出按不可信内容处理”的原因。

### S2｜B 站视频经常“没有字幕”

- **背景**：yt-dlp 对 B 站 CC/AI 字幕的暴露不稳定，总结经常短路。
- **任务**：让 B 站视频尽量能总结。
- **行动**：先用 `view` API 拿 `aid/cid`，再调 `dm/view` 拿字幕列表，优先 `zh/zh-Hans`，下载 JSON 的 `body` 归一化成 `{start,end,text}`；失败再回退 yt-dlp 的人工/自动字幕。
- **结果**：B 站有 CC 的视频基本都能出总结；无字幕时给明确提示而不是报错。
- **反思**：平台特化要有兜底，单点失败不能阻断主流程；但特化代码也会随平台改版腐烂，需要监控。

### S3｜抖音分享链接又短又有水印还有风控

- **背景**：抖音链接是短链，直接给 yt-dlp 不稳定，且默认带水印。
- **行动**：先跟随重定向拿真实 URL，从 query/path 提取视频 id；优先调 `iteminfo` 公开 API，失败则请求分享页，用括号匹配从 `window._ROUTER_DATA` 里抠 JSON；遇到 WAF 挑战就解 base64、暴力搜索 nonce 使 SHA256 匹配，写 cookie 重试；播放地址把 `playwm` 换成 `play` 去水印；下载用 `.part` 再原子替换。
- **结果**：多数分享链接无需 Cookie 可解析。
- **反思**：这是军备竞赛，PoW 暴力搜索有 CPU 放大风险，生产上要限流、缓存 cookie、快速失败；也要注意平台条款与版权合规。

### S4｜思维导图导出的 PNG 只有半个屏

- **背景**：markmap 渲染的是带 `foreignObject` 的 SVG，直接 `drawImage` 会空白或被视口裁剪。
- **行动**：克隆 SVG，把 `foreignObject` 替换成 `<text>`（保留文字与坐标）；用根 `<g>` 的 `getBBox()` 拿内容边界，再按 `translate/scale` 修正；设置完整 `viewBox`，按 4x（至少 3840 宽）放大画到 Canvas；SVG 导出则重设 viewBox 并内联 markmap 的 CSS。
- **结果**：导出的 PNG 是完整 4K 图，SVG 可独立打开。
- **反思**：浏览器渲染管线的细节（transform、foreignObject、taint）不查文档根本想不到；遇到“导出空白”要先怀疑坐标系和安全限制。

### S5｜Stripe Webhook 重试会不会重复加会员

- **背景**：Stripe 至少一次投递，网络抖动会重发。
- **行动**：订单先落 `pending`；Webhook 里用 `WHERE stripe_session_id=? AND status='pending'` 条件更新，更新不到就说明已处理；订单与用户 VIP 在同一事务里改；续期基准取 `max(now, 当前到期时间)`，避免提前续费缩短时长。
- **结果**：重放同一事件不会重复加时长；并发回调也只有一个能成功。
- **反思**：分布式系统默认“至少一次”，消费端必须幂等；更进一步要核对金额、加事件表和对账任务。

## 5. 题库（按模块，答案是要点）

### A. 项目与架构

**Q1. 用一句话介绍项目。**
> 输入视频链接，解析并下载 1800+ 平台的视频；同时提取字幕，用 DeepSeek 做流式总结、思维导图、字幕导出和问答；带 JWT 登录、每日配额和 Stripe 会员。

**Q2. 为什么做这个项目？**
> 真实需求：离线保存 + 长视频先看摘要。技术上想练三条链：多平台解析的工程化、流式 AI 的端到端、商业闭环（认证/配额/支付）。也刻意选了有“脏活”的平台（抖音、B 站）来练降级与反爬。

**Q3. 画一下架构。**
> 按第 3 节图 1 画；强调：前端不直连第三方、同步库丢线程池、AI 与支付都是异步/外部依赖。

**Q4. 这个项目你做了什么？**
> 跟做 + 源码复盘：通读 9 个后端文件和前端核心组件；做了 6 个破坏性实验；发现并验证 P0 级问题（总结流阻塞事件循环、chat 漏鉴权、缩略图 SSRF、JWT 默认密钥、v-html XSS）；做了 AsyncOpenAI / chat 配额 / DOMPurify 等改造实验；补了学习与面试文档。

**Q5. 最大的难点是什么？**
> 不是单个 API，而是“不稳定依赖的组合”：平台会改版、字幕时有时无、模型会慢、支付会重试。项目的应对是分层降级 + 明确事件契约 + 幂等消费。面试时展开 S1/S2/S5。

**Q6. 为什么前后端分离？**
> 前端要处理流式渲染、导图、文件下载，后端要跑 yt-dlp/大模型，资源模型不同；分离后前端可静态托管、后端可独立扩容。代价是跨域、鉴权、联调成本，开发期用 Vite proxy 解决。

**Q7. 如果重做，你会怎么设计？**
> 保留分层；改五处：① 全异步（AsyncOpenAI/async httpx）；② 下载任务队列化 + 专用 worker；③ 配额/限流放 Redis；④ Postgres + 对象存储 + 签名 URL；⑤ 从第一天补测试、日志、Docker。支付加金额对账和事件表。

### B. FastAPI / 异步

**Q8. 为什么选 FastAPI？**
> 原生 async、Pydantic 校验、自动 OpenAPI 文档、依赖注入、SSE 支持；Python 生态和 yt-dlp/OpenAI SDK 同语言，省一个服务。

**Q9. 项目里哪些地方用了 async？**
> 路由都是 `async def`；yt-dlp、字幕提取、导图生成用 `run_in_executor` 丢线程池；SSE 用异步生成器逐个 `yield`；httpx 缩略图代理是 async。

**Q10. 在 async 路由里直接调同步库会怎样？**
> 阻塞事件循环：同一进程内其他请求、心跳、SSE 都排队。yt-dlp 这种秒级操作必须丢线程池；**但项目的总结流仍在 async 生成器里同步迭代 OpenAI 流，这是一个真实缺陷**（P0-2），应换 AsyncOpenAI。

**Q11. `run_in_executor(None, ...)` 有什么问题？**
> `None` 用默认 ThreadPoolExecutor，容量有限且和其他阻塞调用共享；长下载会占满池子导致解析排队；没有超时/取消。应使用专用池 + 信号量 + 超时。另外 `get_event_loop()` 在协程里已弃用，应改 `get_running_loop()`。

**Q12. Pydantic 在这里做了什么？**
> 请求体校验与类型转换（`ParseRequest/DownloadRequest/SummarizeRequest/...`）；字段默认值；校验失败自动 422；也让 OpenAPI 文档可用。

**Q13. `Depends(get_current_user)` 的原理？**
> FastAPI 依赖注入：解析 `HTTPBearer` 拿 token → `decode_token` → 按 `sub` 查库 → 返回 user；失败抛 401。`get_optional_user` 是可选版本，没 token 返回 None。

**Q14. 为什么错误有时返回 400，有时 SSE 里发 error 事件？**
> 请求还没开始流式响应时，可以抛 `HTTPException` 改状态码；一旦 SSE 开始（200 已发出），状态码不能再改，只能发 `error` 事件。前端必须两种都处理。

### C. SSE / 流式

**Q15. SSE 是什么？和 WebSocket 的区别？**
> Server-Sent Events：基于 HTTP 的单向文本流，`Content-Type: text/event-stream`，帧由 `event/data/id/retry` 和空行组成。WS 是全双工、独立协议、需握手与连接管理。这里只需要服务端推 token，SSE 更轻、过代理更好、浏览器原生支持重连。

**Q16. 为什么不用 EventSource？**
> EventSource 只支持 GET、不能自定义请求头；本项目要 POST JSON（url/language）并带 `Authorization: Bearer`。所以用 `fetch` + `response.body.getReader()` 自己解析。

**Q17. 前端解析器怎么写的？**
> `TextDecoder` 流式解码 → 累积 buffer → 按 `\n` 切行，最后一行留到下次 → 空行触发 `dispatch()` → 解析 `event:`/`data:`，多行 data 用 `\n` 拼接 → 按事件名调回调；流结束再 flush 一次。注释行 `:` 忽略。

**Q18. 为什么每个 token 要 JSON 编码？**
> token 可能含 `\n`，而 SSE 用空行分帧、多行 `data:` 会被拼接；直接发会被拆帧或丢格式。`json.dumps` 把换行转义成 `\\n`，前端 `JSON.parse` 还原。这是项目里最典型的“协议边界”问题。

**Q19. 事件为什么这样设计？**
> 按阶段拆：`subtitle` 先让用户看到字幕，`summary` 流式给正文，`mindmap` 在总结后一次性给，`quota` 给剩余次数，`done` 收尾，`error` 统一业务错误。好处是前端可渐进渲染、可观测、可扩展。

**Q20. SSE 断线怎么办？心跳？代理缓冲？**
> 原生 EventSource 会自动重连并带 `Last-Event-ID`；本项目手写解析，没做重连，需要自己加指数退避 + 续传 id。生产要加 15s 注释帧 `: ping` 防中间层超时；Nginx 要 `proxy_buffering off`、`proxy_read_timeout` 调大，否则会“攒着一次性返回”。另外解析器只按 `\n` 切行，若中间层改成 CRLF，空行会变成 `\r` 导致事件不派发，稳妥做法是先 `trim('\r')`。

**Q21. 客户端关闭页面，后端会停吗？**
> 不一定会立刻停。异步生成器通常在下次 `yield` 时才感知断开；同步迭代 DeepSeek 流期间无法感知，会继续烧 token。应在 `finally` 里关闭上游流，或定期检查 `request.is_disconnected()`。

**Q22. SSE 和轮询/长轮询比？**
> 轮询有延迟和无效请求；长轮询实现简单但连接复用差；SSE 是标准流、开销小、天然适合 token 推送。代价是单向、需要处理代理和连接数。

### D. 下载 / 抖音

**Q23. yt-dlp 为什么能支持 1800+ 平台？**
> 它内置大量 extractor，每个站点实现“取页面/接口 → 解析出 info dict（formats/字幕/元数据）”；社区持续跟进改版。项目只做封装与归一化，不自研解析。

**Q24. `format_id` 是什么？`bestvideo+bestaudio/best` 呢？**
> yt-dlp 给每个可用流一个 id；高清视频常把画面和声音分开，所以用 `+` 组合两个流，`/` 表示前面的失败再退回 `best`。合并需要 ffmpeg。

**Q25. 没有 ffmpeg 会怎样？**
> 无法合并音视频；项目检测不到 ffmpeg 时把含 `+` 的格式降级成 `best`，避免直接报错；代价是画质/音质可能下降。

**Q26. 直链和服务端代理怎么选？**
> 直链省服务器带宽、支持断点续传，但受 Referer/签名/时效限制；代理兼容性最好，但吃带宽和磁盘。项目实现了两种，前端实际只用了代理（文档说优先直链，属于漂移）。

**Q27. 为什么抖音要单独写？**
> 短链、分享文案、水印、风控、接口签名都和标准 extractor 不同；yt-dlp 对抖音的支持不稳定。单独模块可以精确控制重定向、id 提取、无水印替换和重试。

**Q28. 描述抖音解析流程。**
> 从分享文案正则取 URL → 跟随重定向拿真实地址 → 从 query（modal_id/item_ids/group_id/aweme_id）或 path（/video/{id}）提取 id → 调 `iteminfo` API → 失败则请求分享页、括号匹配提取 `window._ROUTER_DATA` → 取 `item_list[0]` → 归一化格式。

**Q29. WAF 那个循环在干什么？**
> 页面里有 `wci="cookie名", cs="base64挑战"`；解 `cs` 得到挑战 JSON，其中 `v.a` 是 base64 前缀、`v.c` 是 base64 目标哈希。代码遍历 candidate 0..1e6，找 `sha256(prefix + candidate)` 的十六进制等于目标；命中后把 candidate 的 base64 写回 `d`，整个 JSON 再 base64 成 cookie 值，用 `wci` 里的名字种 cookie，然后重试页面。本质是工作量证明，搜索空间小所以能暴力解。

**Q30. 这个 WAF 方案有什么风险？**
> 单请求最多 100 万次 SHA256，CPU 放大、可被刷成 DoS；平台改算法就失效；也涉及平台条款。生产应限并发/次数、缓存 cookie、超时快速失败，并评估合规。

**Q31. 下载文件怎么清理？大文件怎么办？**
> 现在只在进程退出时清空 `downloads/`；长跑会堆积，且同名会覆盖。应响应后用 `BackgroundTask` 删除、按请求建临时目录、定时兜底清理。大文件不该整段进前端内存，应该直链/签名 URL/流式下载。

### E. 字幕 / AI

**Q32. 字幕获取策略？**
> B 站先走专用 API；其他平台用 yt-dlp 的 `subtitles`（人工）和 `automatic_captions`（自动）；语言优先级 `zh-Hans > zh > zh-CN > en > ja > ko`；人工优先于自动；都没有就返回 `has_subtitle=false`，前端提示。

**Q33. 为什么 B 站要单独做？**
> yt-dlp 对 B 站 CC/AI 字幕的暴露不稳定；B 站自己的 `view`（拿 aid/cid）+ `dm/view`（拿字幕列表）更直接，且能区分人工/AI 字幕（`lan` 前缀 `ai-`）。

**Q34. VTT 怎么解析？**
> 按空行分块；正则匹配 `HH:MM:SS.mmm --> ...`；去掉 `<...>` 标签；同一文本去重（自动字幕常重复）；转成 `{start,end,text}` 秒级结构。字幕文件先下到临时目录，用完即删。

**Q35. 为什么截断 15000 字符？**
> 控制上下文长度和成本，避免超模型窗口；代价是长视频丢尾部信息。更好的做法是分段总结再汇总（map-reduce），或按章节切片 + 只对关键段做精读。

**Q36. Prompt 怎么设计的？**
> 角色（视频分析助手）+ 固定结构（概述/大纲/要点/总结）+ 约束（中文、Markdown、只输出内容）+ 防幻觉（问答要求“视频里没有就诚实说明”）；导图 prompt 强制标题层级，方便 markmap 解析；temperature 0.7 总结、0.5 导图。

**Q37. 思维导图怎么生成和渲染？**
> 非流式调 DeepSeek 生成 Markdown 标题树 → SSE `mindmap` 事件 → 前端 `Transformer.transform` 成树 → `Markmap.create` 渲染 SVG；支持全屏 `fit()`、缩放拖拽。

**Q38. 没有字幕的视频怎么办？**
> 当前直接提示无法总结。扩展方案：Whisper/语音识别转写（成本高、慢），或让用户上传字幕，或只做元数据摘要。要在产品上明确告知，避免用户白等。

**Q39. 大模型成本怎么控？**
> 截断、按语言/视频 id 缓存总结、免费额度、限制并发、失败不扣费、监控 token 消耗；更高阶用便宜模型做初筛、贵模型做精读，或对小请求合并。

### F. 认证 / 配额

**Q40. JWT 怎么工作？为什么用 HS256？**
> 服务端用密钥对 header.payload 签名，客户端带回 `Authorization: Bearer`；服务端验签 + 检查 `exp`。HS256 是对称算法，单服务共享密钥最简单；多服务/第三方验证可换 RS256。`sub` 存 user id（PyJWT 要求字符串，再转 int）。

**Q41. 为什么用 bcrypt？**
> 自带随机盐、可调 cost、故意慢，抗彩虹表和暴力破解；SHA256 太快，不适合存密码。bcrypt 只存哈希，验证用 `checkpw`。

**Q42. JWT 无状态的优缺点？怎么登出？**
> 优点：不存 session、易水平扩展；缺点：签发后无法主动失效、泄露窗口长。登出目前只是前端删 token；要做服务端失效需要黑名单（Redis，TTL 到 exp）或短期 access + refresh token。

**Q43. token 放 localStorage 有什么风险？**
> XSS 可以直接读走；对比 httpOnly cookie 可防 JS 读取，但要处理 CSRF。项目同时有 `v-html`，风险叠加。缓解：CSP、输出消毒、短期 token、刷新令牌轮换。

**Q44. 配额怎么实现的？**
> `users` 表存 `daily_summary_count` 和 `last_summary_date`；UTC 日期不同则重置为 1；VIP 且未过期返回 `remaining=-1`；免费用户满 3 次拒绝。前端用 `quota` 事件显示剩余。

**Q45. 配额并发为什么会超发？**
> “读 count → 判断 → update”不是原子操作；两个请求同时读到 2，都判断可放行，最后都加 1。单进程下也可能因线程调度出现。修法：一条 `UPDATE ... SET count=count+1 WHERE id=? AND (date<>? OR count<?)` 看 `rowcount`，或用 Redis `INCR` + 当日 TTL，或事务里 `BEGIN IMMEDIATE`。

**Q46. 这个项目配额还有别的问题吗？**
> 有：① 先扣配额再提取字幕，没字幕也扣，用户白损失；② chat 接口完全没配额/登录校验，VIP 功能被免费无限用；③ 跨时区按 UTC 重置，国内用户早上 8 点重置，产品上要考虑。

### G. 数据库 / 支付

**Q47. 为什么用 SQLite？WAL 是什么？**
> 零运维、单文件、标准库自带，适合教学/单机；WAL 让读和写不互相阻塞（多读一写），比默认 rollback journal 并发好。代价：单写者、跨机共享难，生产高并发要换 Postgres。

**Q48. 索引和唯一约束起了什么作用？**
> `email` 唯一防重复注册、加速登录；`order_no` 唯一便于查单；`stripe_session_id` 唯一防同一会话建多单；`user_id` 索引加速订单列表。唯一约束也是幂等的一部分。

**Q49. 事务和幂等怎么做的？**
> `get_db()` 上下文管理器统一 commit/rollback；`complete_order` 在同一个连接里先 `SELECT ... FOR`（SQLite 用条件 WHERE）再更新订单和用户；条件 `status='pending'` 保证只有一个请求能改成功。

**Q50. 描述 Stripe 支付流程。**
> 登录 → 创建 pending 订单 → `checkout.Session.create`（price_id、mode=payment、success/cancel URL、metadata、client_reference_id）→ 返回 checkout_url → 用户支付 → Stripe 回调 Webhook → 验签 → 只处理 `checkout.session.completed` 且 `payment_status=paid` → `complete_order` 更新订单与 VIP。

**Q51. Webhook 验签防什么？**
> 防伪造/重放：`stripe.Webhook.construct_event(payload, sig_header, secret)` 用签名密钥验证请求确实来自 Stripe 且内容未被篡改；没验签任何人都能 POST 一个“支付成功”。

**Q52. 会员续期怎么算？**
> `base = max(now, 当前到期时间)`，再 `+1 month`（`relativedelta`，不是 30 天）或 `+1 year`；这样提前续费不会缩短时长，过期续费从当前时间起算。

**Q53. 支付这块还缺什么？**
> 没核对 `amount_total` 与订单金额；`plan_type` 只用于算时长；创建会话失败会留下 pending 订单；没有 failed/refunded 状态和对账任务；`yearly` 在 DB 有分支但 API 的 `PLANS` 只有 monthly，属于死代码。

**Q54. 支付成功页为什么可能显示还不是 VIP？**
> 前端跳 success_url 与 Stripe 发 Webhook 是两条异步路径；页面 1 秒后 `fetchMe` 时 Webhook 可能还没到。应轮询 `/me` 或后端在 success 页校验 session 状态，不能只依赖前端定时。

### H. 前端

**Q55. 为什么用 Composition API / `<script setup>`？**
> 逻辑按功能聚合、类型/提示友好、少写 `this`；`<script setup>` 编译期优化更好。项目组件多是小而专的展示组件，配合 `ref/computed/watch` 足够。

**Q56. 状态为什么放在 `App.vue`？为什么不用 Pinia？**
> 组件树浅（App → 两三个业务组件），props/emit 足够；引入 Pinia 会增加样板。规模变大（多页面、跨组件共享、缓存）时再引入，同时配 Vue Router。

**Q57. `:key="summaryKey"` 的作用？**
> 强制销毁重建 `VideoSummary`，让它重新执行 `onMounted` 里的总结请求，并清空上一次的摘要/字幕/导图/对话。代价是丢失组件内部状态、重建 markmap；更优雅的是暴露 `reload()` 或 watch `videoUrl`。

**Q58. SSE 在前端怎么接状态？**
> `summaryText += token` 驱动 Markdown；`subtitleData` 直接替换；`mindmapMarkdown` 触发 `nextTick` 后渲染；`quotaInfo` 控制提示；`loading` 通过 `watch` 上抛给父组件禁用按钮。

**Q59. 流式 Markdown 有什么性能问题？**
> 每来一个 token 就整段 `marked.parse` + `v-html`，是 O(n²)；长文本会卡。优化：50–100ms 节流、只追加纯文本、结束后再终渲染，或用增量解析器。

**Q60. markmap 导出 PNG 的难点？**
> ① SVG 里的文字在 `foreignObject`（HTML），部分浏览器转 Canvas 会空白或污染；要替换成 `<text>`。② `getBBox()` 是元素局部坐标，不含自身 `transform`，要手动叠加 `translate/scale`。③ 要设完整 `viewBox` 并按 4x 放大，才能导出 4K 全图。④ 要内联 markmap 的 CSS，否则样式丢。

**Q61. SVG 导出呢？**
> 克隆 SVG → 修掉含 `NaN` 的 transform → 用内容 bbox 重设 `viewBox/width/height` → `XMLSerializer` 序列化 → 补 `xmlns` → 把页面中含 `.markmap` 的 `<style>` 内联进 `<defs>` → Blob 下载。

**Q62. SRT 和 VTT 的区别？**
> VTT 有 `WEBVTT` 头、时间用 `.` 分隔毫秒、支持 cue 设置/样式；SRT 用 `,` 分隔毫秒、序号 + 时间行 + 文本。项目两套格式化函数分别处理，TXT 只输出文本。

**Q63. `v-html` 有什么风险？**
> AI 输出/字幕是不可信内容，`marked` 默认允许原始 HTML，可能被 Prompt 注入成 `<img onerror=...>` 造成 XSS。要 DOMPurify 消毒、禁用 raw HTML、加 CSP；用户输入的内容永远不要直接 `v-html`。

### I. 安全 / 工程化

**Q64. 这个项目有哪些安全问题？**
> ① 缩略图代理 SSRF（任意 URL）；② JWT 默认密钥；③ `v-html` XSS；④ 下载/解析无限流，可被当代理；⑤ CORS 通配 + credentials；⑥ 注册接口可枚举邮箱；⑦ chat 未鉴权。按 P0/P1 排序讲。

**Q65. SSRF 怎么防？**
> 域名/协议白名单；解析 DNS 后拒绝私有网段（10/172.16/192.168/127/169.254/::1）；禁止重定向到内网；限制响应大小/类型/超时；出网走代理并审计。

**Q66. CORS 配置有什么问题？**
> `allow_origins=["*"]` 与 `allow_credentials=True` 在规范上不能共存（浏览器会拒绝带凭据的通配响应）；项目用 Bearer 头所以实际影响有限，但仍是坏味道。生产应按环境配置白名单，不需要 cookie 就关 credentials。

**Q67. 怎么限流？**
> 网关/Nginx 按 IP；应用层 slowapi 按 IP+用户；下载/解析单独更严的配额；SSE 限制并发连接数；对 429 返回 `Retry-After`。分布式用 Redis 令牌桶。

**Q68. 怎么部署？SSE 要注意什么？**
> 前端 `npm run build` 静态托管；后端 uvicorn（多 worker 时注意 SQLite 写竞争）；Nginx 反代 `/api`，SSE 关闭 buffering、调大读超时、开启 chunked；HTTPS；环境变量注入；健康检查；日志收集。长任务多时上队列和独立 worker。

**Q69. 怎么测试这个项目？**
> 后端 pytest + httpx AsyncClient：健康检查、注册登录、配额超限、无字幕、Webhook 幂等；mock yt-dlp/DeepSeek/Stripe，保证离线；SSE 用流式响应断言事件序列；前端 Vitest 测解析器和格式化函数；E2E 用 Playwright 走一条主流程。

**Q70. 日志和监控怎么做？**
> 结构化日志（request id、用户 id、耗时、事件）；指标：解析成功率/P95、字幕命中率、总结 token 数、支付成功率、SSE 连接数；Sentry 抓异常；告警看错误率和成本。

**Q71. SEO 和 GEO 做了什么？**
> TDK、canonical、OG/Twitter、三种 JSON-LD（WebApplication/FAQPage/HowTo）、`noscript` 全量内容保证不执行 JS 也能抓、robots 显式允许 GPTBot/ClaudeBot 等、sitemap；GEO 的核心是结论先行、结构化、可被 AI 引用。还发现 SEO 文案与代码配额不一致，属于需要修的产品问题。

**Q72. 版权和合规怎么考虑？**
> 页面有免责声明，只允许下载有版权/授权的内容；不存储用户视频（临时文件）；限流防滥用；尊重平台 ToS；提供举报/下架通道。面试时主动提，体现边界意识。

## 6. 陷阱题与诚实回答

### T1.“这是鱼皮的项目吧？”

> “是，我是跟着教程完成的。但我不想只停在‘跑通’：我通读了后端 9 个文件和前端核心组件，做了 6 个破坏性实验，发现并验证了几个真实问题，比如总结流在 async 生成器里同步迭代会阻塞事件循环、chat 接口漏了配额、缩略图代理可以 SSRF。我做了 AsyncOpenAI、chat 鉴权、DOMPurify 的改造实验。所以这个项目对我来说不只是抄一遍，而是一次源码级复盘。”

### T2.“上线了吗？多少用户？有营收吗？”

> “没有上线。它是教学/个人项目，我没有真实用户和营收数据，也不会编。我能提供的是：完整的功能链路、可复现的本地实验、以及一份‘上生产还差什么’的改造清单。如果您关心工程判断，我可以展开讲 P0/P1 问题怎么排优先级。”

### T3.“1800+ 平台你们怎么验证的？”

> “1800+ 是 yt-dlp 官方支持列表的数量，不是我们逐个测过。我实测覆盖了 B 站、YouTube、抖音等主流平台；长尾平台依赖 yt-dlp 的 extractor，平台改版时可能失效，所以生产上要有失败率监控和快速升级机制。”

### T4.“你说是你做的，具体讲一行代码。”

> 准备三个可落地的点：`summarizer.py` 的 token JSON 编码、`database.py` 的 `complete_order` 条件更新、`VideoSummary.vue` 的 `buildExportableSvg`。能说出文件、函数、为什么这么写。

### T5.“为什么不用微服务 / Redis / 消息队列？”

> “当前规模不需要。单机 + SQLite 足够跑通；引入微服务会带来部署、链路追踪、事务一致性的成本。真正需要的是把长任务（下载/转码）队列化、把配额放 Redis——这是我在改造清单里排的 Phase 1。技术选型要看阶段，不是越多越好。”

### T6.“这个项目最大的缺点是什么？”

> “最大的技术债是异步不彻底：yt-dlp 和导图进了线程池，但最耗时的总结流仍在事件循环里同步跑，会拖慢所有并发请求；其次是配额不原子、chat 没鉴权。这两个是我如果有一周会先修的。”

### T7.“你最大的贡献/最难的地方？”

> 不夸大“从 0 设计”。讲：把不稳定的第三方能力做成可降级链路；把流式协议边界处理干净；把支付幂等做对；以及发现并验证了上述缺陷。

### T8.“如果面试官说‘这不就是个套壳 yt-dlp + OpenAI’？”

> “下载内核确实是 yt-dlp，模型是 DeepSeek，我没有自研。但这个项目的价值在集成层：多平台结果归一化、抖音特化、字幕三级回退、SSE 事件契约、配额与支付闭环、导图导出。这些是‘套壳’不会自动有的。而且我能指出集成层的坑和修法，这比自研一个不稳定的下载器更务实。”

## 10. 回答节奏与救场话术

**结构**：结论（1 句）→ 方案（2–3 点）→ 取舍/代价（1 点）→ 结果或反思（1 句）。

**不会时**（三步）：

1. 先承认边界：“这块我没有在生产环境做过，但我理解它的原理是……”
2. 给最近的知识：“在这个项目里对应的是……，我当时观察到……”
3. 给验证路径：“如果让我做，我会先写一个最小复现/压测来验证，指标看……”

**被追问到不会**：
> “这个点我确实没深入，回去我会从 X 入手补。基于现在的理解，我猜是 Y，因为 Z；如果不对，您能指一下方向吗？”

**不要说的话**：
- “教程就是这么写的。”
- “应该没问题吧。”
- “我们用户很多/性能很好”（无数据）。
- 把“了解”说成“精通”。

**收尾**：
> “这个项目让我完整走了一遍从解析下载、字幕、流式 AI，到认证配额、支付和 SEO 的链路。它不完美，但我知道每一处为什么不完美、以及怎么改。这是我目前最有把握讲深的一个项目。”

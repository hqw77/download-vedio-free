## 1. 一页速览

### 1.1 一张图

```
浏览器 App.vue:215
  │ POST /api/parse { url }
  ▼
FastAPI main.py:103
  ├─ is_douyin_url(url)? ── 是 ──> DouyinParser.parse ──┐
  └─ 否 ──> VideoDownloader.parse_video ────────────────┤
                │ yt_dlp.extract_info(download=False)     │
                ▼                                        │
        _extract_formats: 过滤 → 去重 → 排序 → 合成 → 截断
                │                                        │
                ▼                                        ▼
        { success: true, data: { title, formats, ... } }
                │
                ▼
        VideoResult 渲染 → summaryKey++ → 自动触发 AI 总结
```

> 两个分支都是同步阻塞调用，所以统一用 `run_in_executor` 丢线程池。

### 1.2 30 秒回答（🟢 必背）

> 前端 POST `/api/parse`，后端先判断抖音：抖音走专用解析器，其他走 yt-dlp；yt-dlp 是同步的，所以丢线程池，避免堵事件循环。拿到 info 后做归一化：只保留有视频轨的格式，按“高度 + 容器 + 是否含音频”去重，按分辨率降序取前 15；如果所有格式都没有音频，就合成一条 `bestvideo+bestaudio/best`，交给下载接口用 ffmpeg 合并。最后返回统一的标题、封面、时长、平台、格式列表。

### 1.3 五个关键事实（🟢）

| # | 事实 | 为什么记 |
|---|---|---|
| 1 | 接口是公开的，没有鉴权 | 后面讲限流/SSRF 的伏笔 |
| 2 | `run_in_executor(None, ...)` 用默认线程池 | 后面讲“池被占满”的伏笔 |
| 3 | yt-dlp 只解析不下载：`extract_info(download=False)` | 区分解析/下载两条链 |
| 4 | 归一化四步：过滤、去重、排序、合成 | 这段代码的核心价值 |
| 5 | B 站实测返回 5 个格式，其中 1 条是合成的 | 讲“为什么需要合成”的证据 |

## 2. 面试怎么讲：三层漏斗

### L1：讲流程（30 秒，🟢）

用 1.2 那段。**说完就停**，不要主动展开线程池大小、去重键、ffmpeg。

### L2：被追问“为什么这么设计”（🟡）

只讲三点，每点 2–3 句：

1. **为什么线程池**：`async def` 不会让 yt-dlp 变异步；不丢线程池会阻塞事件循环，`/api/health`、别人的 SSE 全排队。
2. **为什么要归一化**：yt-dlp 的 info 有上百个字段、每个平台不一样；不归一化，前端要兼容上千个 extractor。
3. **为什么要合成 merged**：B 站/YouTube 高清是 DASH，音视频分离；原始格式全是 video-only，必须用 `bestvideo+bestaudio` 组合再合并。

### L3：被追问“有什么问题”（🟡 → ⚪）

按严重度讲，最多讲两条，留一条等他再问：

- 没超时、默认池共享、线程不能真正取消。
- 没 ffmpeg 时降级成 `best`，对 B 站无效（实测 400）。
- 直链传合成 ID 会只返回视频轨（潜在 bug）。
- 无鉴权/限流/缓存，存在 SSRF 面。

**停顿信号**：
- 他点头、换话题 → 停。
- 他问“为什么/然后呢/有问题吗” → 下一层。
- 他看简历/看时间 → 一句话收尾：“这块我踩过坑，需要的话我可以展开。”

## 4. 三个设计取舍（🟡 面试官最想听）

| 决策 | 替代方案 | 选它的理由 | 付出的代价 |
|---|---|---|---|
| `async def` + 线程池 | 直接 `def` 路由；进程池；队列 | 显式、灵活，能塞异步分支 | 默认池共享、无超时、线程不可强杀 |
| DTO 归一化 | 原样透传 yt-dlp formats | 前端稳定、UI 简单 | 丢 codec/fps/HDR/码率；去重“先到先得” |
| 合成 `bestvideo+bestaudio/best` | 前端自己拼；只给纯视频 | 一行选择器解决 DASH 合并 | 依赖 ffmpeg；大小不准；直链丢音频 |

**讲取舍的句式**：

> “我选 A 不是因为它最好，而是因为当前阶段 B 的成本更高；A 的代价是 C，如果规模上来我会换成 D。”

## 5. 四个真实缺陷（🟡，按严重度）

### 5.1 没有超时、默认池共享、线程不能真正取消（P1）

- **现象**：慢站点解析会一直占着线程；几个下载/字幕任务就能把默认池占满，解析开始排队。
- **原因**：`run_in_executor(None, ...)` 用默认池（约 `min(32, CPU+4)`），没有 `wait_for`、没有专用池；即使取消 Future，线程里的 yt-dlp 还在跑。
- **影响**：延迟抖动、请求堆积、资源泄漏。
- **修法**：专用 `ThreadPoolExecutor` + 信号量；`socket_timeout`/`retries`；要强杀用子进程/进程池；或队列化。
- **话术**：“这里最该补的是超时和隔离。现在解析、下载、字幕共用一个默认池，长任务会互相饿死。”

### 5.2 没 ffmpeg 时降级成 `best`，对 B 站无效（P1，已实测）

- **现象**：不装 ffmpeg，下载 1080p 直接 400：`Requested format is not available`。
- **原因**：`download_video` 检测到无 ffmpeg 且 `format_id` 含 `+`，就降级成 `best`；但 B 站只有 video-only 流，没有 combined `best`。
- **影响**：UI 展示了“1080p 最佳（合并）”，用户一点就失败；不是优雅降级。
- **修法**：无 ffmpeg 时隐藏合并项或明确提示；或返回“请安装 ffmpeg”；更好的是服务端内置 ffmpeg。
- **话术**：“这个兜底对 YouTube 可能有效，对 B 站无效。我实测过，所以知道它不是‘降级’，是‘换个方式报错’。”

### 5.3 直链传合成 ID 会丢音频（P2，潜在）

- **现象**：`/api/direct-url` 传 `bestvideo+bestaudio/best`，返回的直链只有视频轨。
- **原因**：`get_direct_url` 先取 `info["url"]`；合成选择器没有顶层 `url`，代码退到 `requested_formats[0]["url"]`，也就是视频流。
- **影响**：前端目前没调用直链接口，所以是潜在 bug；一旦启用就是“下载下来没声音”。
- **修法**：合成格式不返回直链，或返回两个 URL + 说明；下载接口才做合并。
- **话术**：“这是我读代码时发现的一个契约不一致：`format_id` 是选择器，不是真实格式 ID，直链接口不该直接接它。”

### 5.4 无鉴权、无限流、无缓存 + SSRF 面（P1/P2）

- **现象**：任何人都能拿这个接口刷 1800+ 平台；`url` 只校验是字符串。
- **原因**：公开工具的设计；`ParseRequest.url: str`，没有 scheme/私网限制。
- **影响**：被当免费代理；yt-dlp 的 generic extractor 可能请求内网 HTTP 页面（SSRF）；重复解析浪费上游。
- **修法**：只允许 http/https；DNS 解析后拒绝私网；出网代理/防火墙；IP+用户限流；URL 级 TTL 缓存 + single-flight。
- **话术**：“解析是公开入口，我最担心的是被当代理刷。除了限流，还要在 URL 层做 scheme 和私网校验。”

## 8. 表达模板

### 8.1 60 秒版（比 30 秒多一层取舍）

> 前端 POST `/api/parse`，后端判断抖音走专用解析，其他走 yt-dlp；yt-dlp 同步，所以丢线程池。拿到 info 后做归一化：过滤掉纯音频，按高度/容器/音频去重，降序取 15 条；如果全是纯视频流，就合成 `bestvideo+bestaudio/best`。这里有两个取舍：一是用线程池换事件循环不被堵，代价是默认池会被长任务占满；二是归一化换前端稳定，代价是丢 codec/fps 信息。实测 B 站会返回 5 条，其中 1 条是合成的，说明合成不是可选优化，是必需路径。

### 8.2 STAR：讲“无 ffmpeg 降级失败”

- **S**：本地没装 ffmpeg，下载 B 站 1080p 直接 400。
- **T**：定位是平台问题、参数问题还是代码降级问题。
- **A**：看 `download_video`，发现无 ffmpeg 时把含 `+` 的格式降级成 `best`；但 B 站是 DASH，没有 combined `best`。装上 ffmpeg 后合并成功。
- **R**：确认这是“降级策略不够细”，不是网络问题；修法是隐藏合并项/明确提示/内置 ffmpeg。
- **反思**：兜底不是“换个参数”就完了，要针对平台能力设计。

### 8.3 收尾句（被问“还有什么想补充”）

> “这条链路的骨架是‘解析 → 归一化 → 合成 → 返回’，但我更想讲的是它的边界：线程池、ffmpeg、直链契约。知道边界在哪，比会背流程更有用。”

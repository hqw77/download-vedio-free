## 1. 项目画像

| 维度 | 内容 |
|------|------|
| 产品名 | SaveAny（AI 万能视频下载总结器） |
| 一句话 | 粘贴视频链接，解析并下载 1800+ 平台的视频，同时用大模型做总结、思维导图、字幕导出和基于字幕的问答 |
| 形态 | 前后端分离的 Web 应用（单页，无路由） |
| 技术栈 | Vue 3.5 + Vite 7 + Tailwind CSS 4 / FastAPI（≥0.135）+ SQLite / yt-dlp / DeepSeek（OpenAI SDK）/ Stripe |

| 项目性质 | **教学项目**（README 明确为程序员鱼皮的项目教程），当前代码是完整实现版，并附带 SEO/GEO 方法论文档 |

**面试定位建议**：不要包装成“公司线上系统”。最稳的定位是：

> “这是一个我从 0 跟做、并做了源码级复盘和二次改造的个人全栈项目。我不仅能讲清楚每个功能怎么实现，还能指出它离生产级差在哪里，并已经动手修了几个关键问题。”

这句话同时解决了“是不是教程项目”的质疑，并把话题引到你准备好的深度内容上。

```
┌────────────────────────────── 浏览器 ──────────────────────────────┐

│   ├─ VideoSummary     4 Tab：摘要 / 字幕 / 导图 / 问答（SSE 消费）    │
│   └─ AuthModal / PricingSection（Stripe 跳转）                      │
└───────────────┬────────────────────────────────────────────────────┘
                │ 开发期：Vite proxy  /api → localhost:8000
                │ 生产期：Nginx 反代（需关闭 buffering 才能流式）
┌───────────────▼────────────────────────────────────────────────────┐
│ FastAPI（单进程 uvicorn）                                           │
│  /api/parse /download /direct-url /proxy/thumbnail  ← yt-dlp        │
│  /api/auth/*                                        ← bcrypt + JWT  │
│  /api/summarize /api/chat（SSE）                    ← DeepSeek      │
│  /api/payment/*（Checkout + Webhook）               ← Stripe        │
│                                                                    │
│  downloader.py ── yt-dlp ── ffmpeg（可选合并）                       │
│  douyin.py     ── requests ── 抖音公开 API / 分享页 / WAF            │
│  summarizer.py ── yt-dlp 字幕 / B 站 API / OpenAI SDK（DeepSeek）    │
│  database.py   ── sqlite3（WAL、外键、行工厂）                       │
└───────────────┬───────────────────────────┬────────────────────────┘
                │                           │
        backend/downloads/            backend/data/app.db
        （临时视频，停机清理）          （users / orders）
```

关键点：

- **前端不直连第三方**：所有解析、下载、缩略图都走后端，规避 CORS 与防盗链。
- **两种下载模式并存**：`/api/direct-url` 拿直链（省服务器带宽），`/api/download` 服务端代理（兼容防盗链）；但前端实际只用了后者（见第 10 节文档漂移）。
- **AI 链路是“字幕优先”**：先拿到字幕文本，才可能总结；字幕拿不到，后面全部短路。
- **支付是异步确认**：前端跳转成功页 ≠ VIP 已开通，真正生效在 Webhook。

## 4. 五条核心链路（面试就讲这五条）

### 4.1 链接解析 → 格式选择（`main.py:103` → `downloader.py:63`）

1. `HeroSection` 提交表单，`emit('parse', url)`；`App.vue:215` 调 `parseVideo(url)`。
2. 前端 axios `POST /api/parse`（`api/video.js:14`），开发期由 Vite 代理到 8000。
3. `main.py:104` 判断是否抖音：`is_douyin_url()` 为真走 `DouyinParser.parse`，否则走 `VideoDownloader.parse_video`。
4. 两者都是**同步阻塞**调用，因此用 `loop.run_in_executor(None, ...)` 丢进线程池，避免堵住事件循环。
5. `downloader.py:66` 用 `yt_dlp.YoutubeDL.extract_info(url, download=False)` 拿到 info dict，再归一化成前端友好的字段。
6. `_extract_formats`（`downloader.py:103`）只保留有视频轨的格式，按 `(height, ext, 是否含音频)` 去重，按高度降序，最多 15 条；若全都没有音频轨，则合成一条 `bestvideo+bestaudio/best` 的“合并”选项。
7. 前端 `VideoResult.vue` 渲染，缩略图走 `/api/proxy/thumbnail`（带 Referer 绕防盗链）。

**设计点**：把 yt-dlp 的“原始 info”收敛成稳定 DTO，是这层的核心价值；否则前端要兼容上千个 extractor 的字段差异。

### 4.2 服务端下载（`main.py:125` → `downloader.py:176`）

1. 用户选 `format_id`，`App.vue:236` 调 `downloadViaServer`，`responseType: 'blob'`，超时 600s。
2. 后端 `download_video` 用 `outtmpl=downloads/%(title)s.%(ext)s` 下载；有 ffmpeg 时设置 `ffmpeg_location` + `merge_output_format=mp4`，否则把含 `+` 的格式降级成 `best`。
3. 返回 `FileResponse`，`Content-Disposition` 带文件名；前端用正则解析文件名，`URL.createObjectURL` 触发 `<a download>`。
4. 抖音走另一条：`DouyinParser.download` → `_download_file` 流式写 `.part` 再原子 `replace`，失败按 1s/2s/4s 退避重试。

**取舍**：代理模式兼容性最好，但吃服务器带宽和磁盘；直链模式省资源，但很多平台有 Referer/时效/签名限制。

### 4.3 AI 总结（`api_summarize.py:74` → `summarizer.py` → `summarize.js`）

这是项目最值得讲的一条链路，分四段：

```
POST /api/summarize
  ├─ 1. 鉴权 + 配额        get_optional_user → check_and_increment_summary
  ├─ 2. 字幕提取（线程池）  SubtitleExtractor.extract
  │      B 站：view API 拿 aid/cid → dm/view 拿字幕列表 → 下载 JSON
  │      其他：yt-dlp subtitles / automatic_captions → 选语言 → 下 VTT → 解析
  ├─ 3. 流式总结（同步迭代） summarize_stream → 每个 token yield 一个 SSE 事件
  ├─ 4. 思维导图（线程池）   generate_mindmap → 一次性 yield
  └─ 5. quota → done
```

SSE 事件契约：

| event | data | 说明 |
|-------|------|------|
| `subtitle` | 完整字幕 JSON（segments + full_text） | 最先发，前端可先展示字幕 |
| `summary` | `JSON.stringify(token)` | 逐 token，**必须 JSON 编码**，否则换行会拆帧 |
| `mindmap` | `{"markdown": "..."}` | 总结完成后一次性发 |
| `quota` | `{"remaining": n, "limit": 3}` | 仅成功路径 |
| `done` | `[DONE]` | 结束哨兵 |
| `error` | `{"message", "need_login", "need_vip"}` | 业务错误也走 200 + event |

前端 `summarize.js:12` 手写解析器：`TextDecoder` 流式解码 → 按 `\n` 切行 → 空行触发 `dispatch()` → 拼接 `data:` 多行 → 按 `event:` 调回调。`VideoSummary.vue:684` 把回调映射到 `summaryText`、`subtitleData`、`mindmapMarkdown`、`quotaInfo`。

**关键细节**：
- `summaryText` 每来一个 token 就 `watch` 触发一次整段 `marked.parse`（`VideoSummary.vue:342`），长文本下是 O(n²) 重渲染，属于可优化点。
- `mindmapMarkdown` 变化后 `nextTick` 再 `Markmap.create`，因为要等 `<svg>` 挂载。
- SSE 是 200 响应，错误也以 `error` 事件返回；前端必须在回调里处理，不能只看 HTTP 状态码。

### 4.4 登录 → 配额 → VIP（`api_auth.py` + `auth.py` + `database.py:104`）

1. 注册：校验邮箱正则、密码 6–50 位 → 查重 → `bcrypt.hashpw` → 插库 → 签发 JWT。
2. 登录：按邮箱取用户 → `bcrypt.checkpw` → 签发 JWT（HS256，72h，`sub` 存 user id 字符串）。
3. 前端把 token 和 user 存 `localStorage`（`auth.js:7`），每次请求手动加 `Authorization: Bearer`。
4. `/me` 每次按 token 里的 `sub` 回库查用户，并**实时计算** VIP 是否过期（`api_auth.py:33`）。
5. 配额（`database.py:104`）：UTC 日期；VIP 且未过期 → `remaining = -1`（不限）；跨天 → 计数重置为 1；否则 `count++`，超过 3 拒绝。
6. 前端根据 `quota` 事件显示剩余次数，`remaining <= 1` 时提示升级。

**设计点**：JWT 无状态，服务端不存 session；代价是无法主动失效（没有黑名单/refresh token）。

### 4.5 支付 → Webhook → 开通 VIP（`api_payment.py` + `database.py:182`）

```
用户点“开通 VIP”
  → POST /api/payment/create-checkout（需登录）
  → 生成 order_no（SA+UTC 时间+用户 id+uuid8），插入 pending 订单
  → stripe.checkout.Session.create(price_id, mode=payment,
        success_url=前端?payment=success&order_no=..., metadata={order_no,user_id,plan_type})
  → 保存 session.id，返回 checkout_url
  → 浏览器跳转 Stripe 收银台，支付
  → Stripe 回调 POST /api/payment/webhook
       验签 construct_event
       仅处理 checkout.session.completed 且 payment_status=paid
       complete_order(session_id, payment_intent):
         SELECT ... WHERE stripe_session_id=? AND status='pending'
         计算 base = max(now, 当前到期时间)
         monthly +1 月 / yearly +1 年（relativedelta）
         UPDATE orders SET status='paid' ...
         UPDATE users SET is_vip=1, vip_expire_at=...
         （同一事务提交）
  → 前端 success_url 页面显示 toast，1s 后 fetchMe 刷新
```

**幂等**：靠 `status='pending'` 条件更新，重复回调第二次查不到 pending 订单，直接返回。**风险**：金额/套餐未与 Stripe 侧核对，`plan_type` 只用来算时长，价格完全信任 `price_id`。

## 5. 关键技术决策（面试最常被追问的一张表）

| 决策 | 备选方案 | 选它的理由 | 付出的代价 |
|------|----------|------------|------------|
| 用 yt-dlp 而不是自研解析 | 各平台单独写爬虫 | 1800+ extractor、社区持续修、省下巨大维护成本 | 依赖重、平台改版会集体失效、同步 API 需线程池包 |
| SSE 而不是 WebSocket | WS、轮询、长轮询 | 单向推送足够；纯 HTTP、易过代理、浏览器原生支持重连 | 只能服务端→客户端；POST 场景要手写解析；代理易缓冲 |
| `fetch + ReadableStream` 而不是 `EventSource` | 原生 EventSource | 需要 POST JSON 和 `Authorization` 头，EventSource 只支持 GET 且不能自定义头 | 自己处理分帧、重连、心跳、编码 |
| SQLite 而不是 MySQL/PG | Postgres、Redis | 零运维、单文件、够用；`sqlite3` 标准库无额外依赖 | 单写者、并发弱、无水平扩展、迁移靠手写 SQL |
| JWT 而不是 Session | 服务端 session + Redis | 无状态、前后端分离友好、实现简单 | 无法主动踢人、续期/刷新要另做、token 泄露窗口长 |
| Stripe Checkout 而不是自建收银台 | 自己收卡、其他支付 | PCI 负担转移给 Stripe；托管页面 + Webhook 标准流程 | 依赖外部服务、回调时序复杂、需要公网 Webhook |
| 同步 SDK + 线程池 | 全异步（AsyncOpenAI/async httpx） | 上手快，yt-dlp 只有同步 API | 线程池会被长任务占满；**总结流仍在事件循环里同步迭代（见 P0-2）** |
| markmap 而不是自绘导图 | d3、canvas 自绘 | Markdown 进、SVG 出，交互/缩放现成 | 导出时要处理 `foreignObject`、transform、CSS 内联 |
| Tailwind 4（CSS-first） | Tailwind 3 + config、UI 库 | 零配置文件，`@theme` 定义设计令牌，构建快 | 新版本生态/插件兼容性、团队熟悉度 |
| 无 Vue Router / Pinia | 全家桶 | 单页 + 组件树浅，`App.vue` 足够 | 页面一多就会 props 钻透、状态难维护 |

## 6. 数据模型

```sql
users(
  id INTEGER PK AUTOINCREMENT,
  email TEXT UNIQUE NOT NULL,          -- 登录名
  password_hash TEXT NOT NULL,         -- bcrypt
  is_vip INTEGER DEFAULT 0,
  vip_expire_at TEXT,                  -- ISO8601， UTC
  daily_summary_count INTEGER DEFAULT 0,
  last_summary_date TEXT,              -- UTC 日期 YYYY-MM-DD
  created_at/updated_at TEXT
)

orders(
  id INTEGER PK,
  order_no TEXT UNIQUE,                -- SA + 时间 + user_id + uuid8
  user_id INTEGER FK → users(id),
  amount INTEGER,                      -- 分（990 = ¥9.9）
  currency TEXT DEFAULT 'cny',
  status TEXT DEFAULT 'pending',       -- pending / paid
  plan_type TEXT DEFAULT 'monthly',
  stripe_session_id TEXT UNIQUE,
  stripe_payment_intent_id TEXT,
  paid_at TEXT,
  created_at/updated_at TEXT
)
```

索引：`users(email)`、`orders(user_id)`、`orders(order_no)`、`orders(stripe_session_id)`。连接级 PRAGMA：`journal_mode=WAL`、`foreign_keys=ON`；`get_db()` 用上下文管理器统一 commit/rollback/close。

**订单状态机**：`pending → paid`（单向，条件更新保证只成功一次）。没有 `cancelled/refunded/failed`，也没有对账任务。

## 7. 前端结构

```
App.vue（状态中枢）
├─ AppHeader           user、登录/注册/退出/开通 VIP
├─ HeroSection         parse 事件；compact/showSlogan 控制首屏收缩
├─ VideoResult         video、downloading、summarizing；emit download/summarize
├─ VideoSummary        videoUrl、user；key=summaryKey 强制重挂载
│    ├─ Tab 摘要        marked → v-html；流式光标
│    ├─ Tab 字幕        时间戳列表；SRT/VTT/TXT 下载
│    ├─ Tab 导图        markmap 渲染；全屏；PNG/SVG 导出
│    └─ Tab 问答        消息列表；流式回答；自动滚底
├─ Feature / HowTo / Comparison / Pricing / Platform / Footer
├─ Teleport 支付 toast
└─ AuthModal           登录/注册，成功回传 user
```

- **状态归属**：登录态、视频数据、下载/总结 loading 都在 `App.vue`，子组件只收 props、发事件；没有 Pinia。
- **`summaryKey` 技巧**：解析成功或点“重新总结”时自增，作为 `VideoSummary` 的 `key`，强制销毁重建 → 重新执行 `onMounted` 里的 `startSummarize()`，同时清空上一次的文本/导图/对话。比暴露 `reload()` 方法更省事，但会丢组件内部状态。
- **自动总结**：`VideoSummary` 挂载即请求，所以“解析成功 → 自动出总结”，按钮只用于重试。
- **支付回跳**：`App.vue:181` 解析 `?payment=success|cancel`，用 `history.replaceState` 清掉 query，再延时 `fetchMe` 刷新 VIP（依赖 Webhook 已处理完，存在竞态）。
- **彩蛋**：非输入框内连按 3 次 Enter 切换 `demoMode`，控制首屏 slogan 是否常显。

## 8. 工程质量：做得好的地方

1. **分层清楚**：入口、下载、平台特化、AI、认证、支付、数据层各自成文件，路由用 `APIRouter` 挂载，没有把逻辑全塞进 `main.py`。
2. **统一 DTO**：抖音模块刻意返回与 yt-dlp 同构的字段（`formats/title/duration_string/...`），前端无需感知平台差异。
3. **降级思维**：B 站专用字幕失败 → yt-dlp；公开 API 失败 → 分享页 HTML；无 ffmpeg → `best`；直链不可用 → 服务端代理。
4. **SSE 细节到位**：token JSON 编码防拆行、事件类型区分、结束哨兵、错误也走事件、前端按规范拼接多行 `data`。
5. **支付幂等**：条件更新 + 唯一约束，重复 Webhook 不会重复加时长。
6. **前端导出是真难点**：`foreignObject → <text>`、`getBBox + transform` 修正、4x 缩放、CSS 内联，这些不是“调库”能解决的。
7. **SEO/GEO 完整度**：TDK、canonical、OG/Twitter、三种 JSON-LD、`noscript` 兜底、AI 爬虫白名单、sitemap，还配了方法论文档。

## 11. 如果上生产：改造路线

### Phase 0（1–2 天，先止血）

1. `AsyncOpenAI` 重写总结/问答流（P0-2），并用并发压测证明 `/health` 不再被拖慢。
2. `/api/chat` 接配额 + 登录校验（P0-1）。
3. 缩略图代理加域名白名单/私网拦截（P0-3）。
4. `JWT_SECRET` 缺失即启动失败（P0-4）。
5. `marked` 输出接 DOMPurify（P0-5）。
6. 全局限流（IP + 用户维度），下载接口加签名/短时 token。

### Phase 1（3–5 天，能稳定跑）

- 配额原子化 + 失败回滚；Redis 存日计数（TTL 到次日 UTC）。
- 下载任务队列化（RQ/Celery/Arq），专用 worker + 并发上限 + 超时；下载完成后 `BackgroundTask` 清理。
- Webhook 金额对账、失败订单状态、每日对账任务。
- pytest + httpx 异步测试（mock yt-dlp/DeepSeek/Stripe），CI。
- Dockerfile + compose（backend/frontend/nginx），健康检查，结构化日志。

### Phase 2（规模化）

- Postgres 替 SQLite；对象存储 + 签名 URL 替本地磁盘；CDN 缓存缩略图。
- 解析结果短缓存（同一 URL 5–10 分钟），总结结果缓存（按视频 id + 语言）。
- 可观测性：Prometheus 指标（解析成功率、P95、token 消耗）、Sentry、trace。
- 内容安全与合规：版权提示、下载频率限制、robots/ToS 评估、举报通道。

## 12. 面试讲述地图（背这一页）

### 6 个可以主动抛的亮点

1. **SSE 事件化设计**：`subtitle/summary/mindmap/quota/done/error` 六类事件，把“慢操作”拆成可感知的阶段；token 用 JSON 编码解决换行拆帧。
2. **字幕三级回退**：B 站专用 API → yt-dlp 人工字幕 → 自动字幕；语言优先级 `zh-Hans > zh > zh-CN > en > ja > ko`。
3. **抖音反爬链路**：短链重定向 → 提取 id → 公开 API → 分享页 `_ROUTER_DATA` 兜底 → WAF PoW → `playwm→play` 去水印。
4. **支付幂等**：`WHERE status='pending'` 条件更新 + `stripe_session_id` 唯一约束，重复回调不重复加时长。
5. **前端导出**：`foreignObject → <text>` 规避 canvas taint；`getBBox + transform` 拿真实内容边界；4x 缩放出 4K PNG；SVG 内联 markmap CSS。
6. **SEO/GEO**：TDK + 三种 JSON-LD + `noscript` 全量内容 + AI 爬虫白名单，兼顾传统搜索与生成式引擎。

### 5 个可以主动承认并给出方案的深挖点

1. 总结流同步迭代阻塞事件循环（P0-2）→ AsyncOpenAI + 并发压测。
2. 配额先扣后验 + 非原子（P1-1/P1-2）→ 成功后扣 + 条件更新/Redis。
3. 缩略图 SSRF（P0-3）→ 白名单 + 私网拦截。
4. `v-html` XSS（P0-5）→ DOMPurify + CSP。
5. Webhook 不核对金额（P1-6）→ `amount_total` 对账 + 对账任务。

### 3 个要诚实说明的边界

- 这是教学项目，不是线上高并发系统；没有真实 DAU/营收数据。
- 1800+ 平台来自 yt-dlp 的支持列表，未逐一验证；实测覆盖 B 站/YouTube/抖音等主流平台。
- 没做过线上压测；性能结论来自本地并发实验（学习计划里有实验步骤）。
